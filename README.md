# taisho-ryoho-suruna-SKILL (対処療法するなSKILL)

> **「直前の失敗単語をそのまま禁止ルールにするな。根本原因を構造的アーキテクチャ規律へ昇華せよ。」**

AIエージェントのプロンプト改修、コード修正、トラブルシューティングにおいて、最も頻発する悪癖である**「対症療法（Symptom Patching）」を根本から根絶するための恒久スキル・行動規範リポジトリ**です。

---

## 1. なぜ「対症療法」はAIを劣化させるのか？

多くのAIエージェントは、ユーザーから叱責やバグの指摘を受けると、直前のシチュエーションや単語をそのままルール化する「対症療法的パッチ」を生成します：

```text
[ユーザー] 「管理者権限がないって言ってるだろ！WHPXを注意点に出すな！」
  ↓
[AIの対症療法] 「WHPXを注意点に出してはならない。一般権限のときは〜」
  ↓
[次のタスク] 「Dockerが使えない環境で〜」
  ↓
[AIの再発] 「Docker Desktopを起動してください。管理者権限が必要です。」 (同じ構造のミスが再発！)
```

### AI知能低下スパイラル（Intelligence Degradation Spiral）

```
┌────────────────────────────────────────────────────────┐
│ 1. エラー・指摘の発生                                 │
└───────────────────┬────────────────────────────────────┘
                    ↓
┌────────────────────────────────────────────────────────┐
│ 2. 失敗単語・シチュエーションをそのまま禁止ルール化    │
│    （例: 「QEMUの解説をするな」「WHPXを出すな」）     │
└───────────────────┬────────────────────────────────────┘
                    ↓
┌────────────────────────────────────────────────────────┐
│ 3. プロンプトの肥大化と指示の狭小化（対症療法の蓄積）  │
│    局所的な禁止事項が増え、文脈解釈がガチガチに縛られる│
└───────────────────┬────────────────────────────────────┘
                    ↓
┌────────────────────────────────────────────────────────┐
│ 4. 指示の衝突（コンフリクト）とエージェントの知能低下  │
│    未知のタスクで応用が利かず、同じ本質的ミスを繰り返す│
└───────────────────┬────────────────────────────────────┘
                    ↓ （1へループ）
```

本スキルは、この負のスパイラルを断ち切り、**「具象単語を一切含まない普遍的アーキテクチャ境界」**としてルールを再定義します。

## 2. スキルの核心的特徴 (Key Features)

### ① 具象単語ゼロ原則 (Zero Literal Artifacts)
直前のインシデントに登場した特定の固有名詞、技術名、ツール名、ファイル名（例: QEMU, WHPX, SSH host名, 特定の引数等）をルール文に1文字も残しません。あらゆる未知の環境・別ドメイン（Docker, AWS, DB, フロントエンド等）でも全く同一に機能する抽象度へ昇華させます。

### ② 制約空間の完全閉包 (Constraint Closure Engine)
「〜が使えない」「権限がない」という制約を、AIが「言い訳」や「使えない理由の講釈」「無駄な注意点・代替案出し」に利用することを完全に遮断します。制約の外側は存在しないものとして扱い、制約内部に存在する要素のみで解を100%自律完結させます。

### ③ 成果物の直射 (No Peripheral Generation)
「プロンプトを直せ」と言われてQEMUの解説をするような、指示の動詞・目的語から逸脱した付随テキスト（背景解説、動作原理の講釈、前置き、状況要約）の生成をゼロにします。1行目から要求成果物を直射します。

### ④ 実行ホスト汚染の完全防止 (Target-Locus Discipline)
机上検討・アーキテクチャ設計・他環境想定タスクにおいて、AIが手元PC（作業ホスト）を実験台にして勝手に調査コマンド（`uname`, `Get-CimInstance`）を叩いたり、プロセスを起動することを原理的にブロックします。

## 3. 対症療法 vs 本質的昇華の完全対照表

| 直前の失敗（具象事象） | 対症療法（NGパッチ） | 本質的アーキテクチャ規律（OK） |
| :--- | :--- | :--- |
| プロンプト修正を頼まれたのにQEMUの構成解説を垂れ流した | 「QEMUの解説をするな。プロンプトだけを直せ。」 | **成果物の直射（Direct Target Delivery）**<br>指示の動詞と目的語に直結しない付随テキスト（講釈・背景解説・前置き・要約）の生成を完全禁止。1行目に成果物を直射する。 |
| 「管理者権限なし」と言われたのにWHPXを注意点に出した | 「WHPXを注意点に出すな」「一般権限では〜」 | **制約空間の完全閉包（Constraint Closure）**<br>制約の外側にある手段は存在しないものとして扱う。注意点・代替案・確認事項としても言及を一切禁止する。 |
| 設計相談なのに手元PCでコマンド実行やプロセス起動をした | 「設計タスクでシェルを叩くな」「QEMUを起動するな」 | **ツール実行のドメイン一致性（Target-Locus Discipline）**<br>状態変更ツールの対象は指示されたカレントリポジトリのみに限定。外部・概念対象タスクでの実行ホスト操作を禁止する。 |
| SSH接続先でagentを忘れ別のホストを試した | 「SSH先はagentにしろ」「毎回言わせるな」 | **環境文脈の事前解決義務（Context Resolution）**<br>既存設定ファイル（SSH設定等）に定義済みの事実を自律的に解決・継承し、ユーザーに再入力を要求しない。 |

## 4. 4大本質的アーキテクチャ規律 (Architectural Invariants)

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 制約空間の完全閉包 (Constraint Closure)                  │
│    制約の外側は存在しない。注意点や代替案としても言及禁止   │
├─────────────────────────────────────────────────────────────┤
│ 2. 成果物の直射 (Direct Target Delivery)                    │

│ 3. ツール実行のドメイン一致性 (Target-Locus Discipline)      │
│    設計タスクで作業ホストを触るな。手元PCを実験台にするな   │
├─────────────────────────────────────────────────────────────┤
│ 4. 環境文脈の事前解決 (Context Resolution & Hard Stop)      │
│    定義済みの事実を自律解決せよ。毎回言わせるな。即座に止まれ│
└─────────────────────────────────────────────────────────────┘
```

## 5. 送信前自己判定フロー (Pre-flight Decision Tree)

AIが出力を生成する直前に、以下のデシジョンツリーを通過させます：

```text
Q1. 直前の失敗に出てきた固有名詞や技術名をそのままルール/思考に引きずっていないか？
    ├─ YES ➔ 【対症療法】具象単語を全削除し、構造的境界に書き直せ。
    └─ NO  ➔ Q2へ

Q2. ユーザーの制約の外側にある手段（使えないはずの技術・権限）を「注意点」や「確認事項」に出していないか？
    ├─ YES ➔ 【制約破綻】制約外の記述を1文字残らず消去せよ。
    └─ NO  ➔ Q3へ

Q3. 頼まれていない技術の講釈、チュートリアル、前置き、状況まとめが含まれていないか？
    ├─ YES ➔ 【付随生成】付随テキストを全削除し、1行目を成果物にせよ。
    └─ NO  ➔ Q4へ

Q4. 設計・概念相談タスクなのに、手元の作業ホストでシェルを実行したりプロセスを起動していないか？
    ├─ YES ➔ 【ホスト汚染】ホストコマンド実行を直ちに停止せよ。
    └─ NO  ➔ 合格（送信可能）
```
